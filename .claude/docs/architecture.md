## Architecture

- **Angular 22, standalone components, zoneless** (no `zone.js` dependency) — change detection relies on signals/explicit triggers, not zone patching. Bootstrapped in `src/main.ts` via `bootstrapApplication`.
- **No UI component framework.** Ionic and Angular Material were both evaluated and removed; components and styles are hand-written (plain HTML/SCSS per component).
- **`ChangeDetectionStrategy.OnPush`** is set on every component and is the schematic default for `ng generate component` (configured in `angular.json`). New components should keep it unless there's a specific reason not to.
- **Path aliases**: `@models/*`, `@services/*`, `@testing/*`, `@utils/*` map to `src/app/core/{models,services,testing,utils}/*`; `@shared` (bare) resolves to the `src/app/shared/index.ts` barrel, `@shared/*` to individual files under `src/app/shared/`. Configured in `tsconfig.json`. Use these instead of relative `../` imports when crossing into `core` or `shared` from elsewhere; within `shared` itself, cross-component imports use `@shared/deep-path` (not the barrel) to avoid circular imports through `index.ts`.
- **`src/app/shared/` is organized into domain subfolders** — `cards/`, `decks/`, `locations/`, `auth/`, `layout/`, `effects/`, `common/`, `ds/`, `gameplay/` — rather than one flat list of component folders. Place new shared components in the matching domain folder; `ds/` holds the new design-system primitives (DESIGN.md), `common/` the legacy subject-agnostic ones, `gameplay/` the Planechase components and flairs; `@shared/*` still resolves through the nesting unchanged.
- **Routing**: `src/app/app.routes.ts` is the single source of route definitions. Route-level ("page") components live under `src/app/views/<name>/`, one folder per view, each with its own `.ts`/`.html`/`.scss`/`.spec.ts`. `home` is the current example and is mounted at the root path (`''`).
- **App shell**: `src/app/app.ts` is the root component. See "Styling / design system" below for its template/layout structure.
- **Static assets** go under `public/assets/` and are served at `/assets/...` at runtime (configured via the `assets` glob in `angular.json`'s build target, which copies everything under `public/` to the app root).
- **Capacitor** (`capacitor.config.ts`) wraps the built web app (`dist/grimorio/browser`, must match the `build` target's output path) for native targets. The `android/` platform has been added (via `npx cap add android`, with `@capacitor/android` as a devDependency) — it's a generated Gradle project, not hand-edited; run `npm run cap:build` after web changes to resync it. No `ios/`/`electron/` platforms have been added.
- **Testing**: unit tests run through Angular CLI's `@angular/build:unit-test` builder, backed by Vitest (not Karma, not Jest) — this is Angular's current default runner and is wired into the same esbuild-based pipeline as `ng build`/`ng serve`.
- **OCR**: `tesseract.js` provides client-side text recognition (used by card scanning to read a card's set code/collector number from a photo). It must always be loaded via dynamic `import()`, never a static import, so it stays out of the initial bundle — the CLI's esbuild-based builder code-splits it into its own lazy chunk automatically. Worker/wasm/language-data assets are fetched from tesseract.js's default CDN at runtime (no assets committed to the repo).
- **Planechase card data**: `src/app/core/data/planechase/` ships `cards.json` (planes/phenomena with image URLs and a text hash) and `cards.pt-br.json` (reviewed translations keyed by id, each with the `sourceHash` it was made from). Both are generated by the maintainer (`npm run sync:planechase`, then the `planechase-translate` skill) and never edited by hand. `PlanechaseCatalogService` loads them only via dynamic `import()` (own lazy chunk), through `planechaseCatalogResolver` on the `/modes/planechase*` routes; a stale or missing translation falls back to English. The app makes no Supabase call for Planechase.
- **`src/app/core/utils/`** holds framework-agnostic pure functions (e.g. `card-ocr.util.ts`). Angular's Vitest builder doesn't support `vi.mock` on relative imports — a util that needs to be mocked in a component test should be wrapped in a thin `providedIn: 'root'` service (see `CardOcrService`) so it can be swapped via a TestBed provider instead.
- **`linkedSignal`** is the idiom for writable local state that resyncs from an input/signal (e.g. `card-add-detail-panel.ts`'s `faceIndex`, reset to `0` whenever `candidate` changes) — distinct from `computed` (pure derivation, not writable) and `effect` (side effects, not state derivation).

## Domain model

- **`CardEntry`** (`src/app/core/models/card.model.ts`) — a printing-level owned card record: identity fields (scryfallId/oracleId, set/collector number, name, rarity, colorIdentity, typeLine, commanderLegality, canBeCommander), physical/ownership fields (finish, language, condition, quantity, `locationId`, forSale, notes), and an optional double-faced `faces[]`.
- **`StorageLocation`** (`src/app/core/models/storage-location.model.ts`) — `{id, name, parentId}`, plus a derived `StorageLocationNode` tree type for nested physical storage.
- **`Deck` / `DeckCard`** (`src/app/core/models/deck.model.ts`) — a `Deck` has `commander: DeckCard | null` and `cards: DeckCard[]`. `DeckCard` is a union: `{source: 'owned', cardEntryId}` referencing an existing `CardEntry`, or `{source: 'freeBuild', card: DeckCardIdentity}` embedding a standalone printing-level identity for cards not in the collection. Both variants are printing-precise (set/collector/finish-level) — never a generic "any printing" reference.
- **Persistence pattern**: `CardService`, `StorageLocationService`, `DeckService` (`src/app/core/services/`) all follow the same shape — signal-backed state hydrated asynchronously from **IndexedDB** (via the `idb` library, `src/app/core/db/`), with full CRUD and `byId` computed lookups. Owned data is partitioned per local profile: IndexedDB `grimorio-device` holds the profile registry and `activeProfileId`, and each profile has its own `grimorio-profile-{id}` database, so isolation holds by construction; the pre-profiles `grimorio` database is deleted on startup (`core/db/legacy-cleanup.ts`). Each service exposes `load(profileId | null)`, `changeCount`,  exposes `whenReady()` (resolves once the latest hydration lands) and `flush()` (resolves once all enqueued writes have landed). Entity services don't hydrate on construction; `ProfileSessionService.whenReady()` (awaited in `app.config.ts`'s initializer after `runLegacyCleanup()` and `ProfileStore.whenReady()`) calls `load(activeProfileId)` on each, so no component ever observes pre-hydration state. Writes go through a private serialized queue (`enqueueWrite`) per service and capture the bound profile DB when enqueued. New entity services should follow this convention. Unit tests need the `fake-indexeddb` polyfill (wired via `src/test-setup.ts`, loaded through `angular.json`'s `setupFiles`) since jsdom has no native IndexedDB; `src/test-setup.ts` also resets every `grimorio-*` database before each test.
- **Planechase state**: `PlanarSelectionService` (the planar deck's disabled card ids) is an entity service in `ProfileSessionService`'s list, stored as the `planarSelection` `meta` record of the active profile's database, or of `grimorio-device` when no profile is active. `PlanechaseGameService` is device-scoped, not per profile: the game in progress (with its one-step undo) is the `planechaseGame` record in `grimorio-device`'s `meta` store, hydrated in the app initializer, and survives profile switches. `PlanarImageService` caches card images in Cache Storage (`grm-planechase-images`) and serves them as object URLs, so seen images work offline. Randomness comes from `crypto.getRandomValues` (`core/utils/crypto-random.util.ts`).
- **Card data source**: `CardLookupService` (`src/app/core/services/card-lookup.service.ts`) resolves a set code + collector number against a **Supabase**-hosted catalog (`printings` joined to `cards` tables; client in `src/app/core/supabase-client.ts`), filled by `npm run sync:scryfall` from Scryfall bulk data; `printings` also carries `border_color`, `released_at`, `image_small` and `image_large`, read by `sync:planechase`. There is no live Scryfall API integration and no price data modeled anywhere. Multi-row lookups (`lookupManyByScryfallIds`, `lookupManyBySetCode`, used by CSV import) batch into one query per distinct key instead of one query per row — new bulk-lookup call sites should follow the same batching shape rather than looping a per-row Supabase call.
- **New Supabase tables**: must ship GRANT statements and owner-only RLS policies (`(select auth.uid()) = user_id`, see `storage_locations`/`card_entries`) in the same migration that creates the table — since 2026-10-30 Supabase no longer auto-grants Data API access to new `public` tables, so a missing grant returns "permission denied". Owner-only tables: `grant select, insert, update, delete on public.<t> to authenticated;` (no `anon` grant). Public catalog tables (`cards`/`printings`): `grant select on public.<t> to anon, authenticated;`. Grant `service_role` only when server-side code needs the table. Any `updated_at` column must be `NOT NULL` with a default — a table without these is unusable from the client and null timestamps break last-write-wins sync reconciliation.
- **Sync**: `CardEntry`/`StorageLocation` both require `updatedAt: string` (ISO timestamp), stamped internally by `CardService`/`StorageLocationService`'s `add`/`update`/`addMany` — callers never pass it themselves, same as `id`. `DeckCardIdentity` (a frozen freeBuild-deck-card snapshot) deliberately excludes `updatedAt` from its `Omit<CardEntry, ...>`. Both services also track soft-delete tombstones (IndexedDB's `tombstones` store), populated by `remove()` and exposed via `getTombstones()`/`clearTombstones()` — sync-only, invisible to every other consumer. `SyncService` (`src/app/core/services/sync.service.ts`) syncs the active profile's locations/cards with its linked account (composite `(user_id, id)` keys, `onConflict: 'user_id,id'`), then its planar deck selection as one reconciled entity (`planechase_selections`, one row per account, `onConflict: 'user_id'`, no tombstones), via a generic reconciler (`reconcileEntities`, `src/app/core/utils/sync-reconcile.util.ts`) using per-row last-write-wins on `updatedAt`; tombstones resolve the "deleted here vs. never synced" ambiguity a remote-only row would otherwise have. Sync starts only from the shell's sync controls (`SyncStatusService.act()`) and the "Excluir perfil" step's in-place sync — never on sign-in, link or switch. Each sync first runs an identity step that reconciles the profile's colors/name with the account's `user_metadata` (`grm_colors`/`grm_label` plus `grm_colors_at`/`grm_label_at`), last-write-wins (`core/utils/identity-sync.util.ts`). The expired state comes from the profile's `cloud.needsReauth` flag, not from the last sync: `SyncService.state()` reports `'reauth'` whenever the flag is set and drops it as soon as any re-sign-in (reauth, reset code, recover) clears the flag. Not extended to decks — the prototype `decks`/`deck_cards` Supabase tables were dropped and need redesigning from scratch, not resurrecting.
- **Mana/card symbol assets**: `public/assets/mana/` holds all 84 MTG mana/card symbol SVGs fetched from Scryfall's `/symbology` API plus a `manifest.json` describing each (symbol, name, colors, hybrid/phyrexian flags). Only the WUBRG + colorless (`C`) icons are wired up so far (legacy `collection-filters`/`location-color-picker`); the rest await future mana-cost rendering. New UI must not use them (DESIGN.md: no Magic symbols).

## Auth

Local profiles (`ProfileStore`, PBKDF2 hashes) are required for owned data; cloud accounts are optional, per profile (`CloudAuthService`, e-mail + password, 6-digit reset code). Entering (pick/unlock/create a profile, reset its password) runs in `EntryModal` (`shared/auth/entry-modal/`, contexts `device | gate`) via `EntryModalService`, state in `EntryFlowStore`. Managing the active profile (colors, name, passwords, link/reauth/unlink, deleting the profile or the cloud account) runs in `ProfileModal` (`shared/auth/profile-modal/`) via `ProfileModalService`, state in `ProfileFlowStore`. Pure rules live in `core/utils/{entry-flow,profile-flow}.util.ts`; all PT-BR copy is centralized in `core/utils/entry-copy.ts`. Only one modal is ever open: each service's `open()` is a no-op while the other is open. The top-bar profile control and the shell's sync area open the profile modal. `/profile` redirects to Home.

- **Shared cloud forms**: `CloudForm`/`ResetForm` (under `entry-modal/`) render in both modals through the abstract `CloudFlowHost` token (`shared/auth/cloud-flow-host.ts`), which each store provides with `{ provide: CloudFlowHost, useExisting: … }`. `fluid-face.ts` (`shared/ds/themed-modal/`) gives both modals a content-driven desktop height and focuses the first field or action row on each screen change.
- **Deletion**: a local profile is deleted via `ProfileLifecycleService` + `deleteProfileDb(id)` (drops `grimorio-profile-{id}`), never touching the cloud. A cloud account is deleted only through the `delete_own_account()` Postgres function (`CloudAuthService.deleteAccount`).
- **Toasts**: `ToastService` (one at a time, replaced by the next, 5 s). `ToastOutlet` hosts sit in `app.html`, `ThemedModal` and the nav drawer; only the most recently pushed active host renders, as a popover, so the toast shows inside the top `<dialog>` (a modal dialog makes everything outside it inert).

- **Route gating**: `profileGuard` (`core/guards/profile.guard.ts`) gates every owned-data route; with no active profile it opens the entry modal and waits. Gated routes also set `runGuardsAndResolvers: 'always'` so a sign-out/switch re-guards the current page. Home, About and the `/modes*` gameplay routes (Planechase) stay ungated.
- **Cloud clients**: one Supabase auth client per linked profile (`CloudSessionService`, localStorage key `grm-cloud:{id}`); the shared `SUPABASE_CLIENT` is anonymous-only (catalog reads). Cloud errors reach the UI only via `mapCloudError` (`core/utils/cloud-error.util.ts`) — never raw Supabase text.

The Supabase project has "Confirm email" disabled, so sign-up signs the account in immediately.

**Modals**: use the native `<dialog>` element (`showModal()`/`close()`), not a library — `ThemedModal` (`shared/ds/themed-modal/`) is the reference pattern for any future modal. Modal components are mounted only while open (`@if` on their service's `isOpen()` in `app.html`), so nothing idles in the DOM; `ThemedModal` opens on mount and closes (restoring focus to the opener) on destroy.

## PWA

`@angular/service-worker` (added via `ng add @angular/pwa`) makes the app installable as a standalone desktop/mobile app. `ngsw-config.json` (project root) configures asset/data caching; `public/manifest.webmanifest` declares the app identity/icons. The service worker is registered in `src/app/app.config.ts` via `provideServiceWorker(...)`, gated on `!isDevMode()` — it's inert under `ng serve` and only active in production builds, which emit `ngsw.json`/`ngsw-worker.js` into `dist/grimorio/browser`. Icons under `public/icons/` are placeholders from the schematic, not final artwork.

## Styling / design system

- **New foundation**: `src/styles.scss` uses only `_tokens` (tokens implementing `DESIGN.md`, the `--role-*` chain redeclared on `[data-theme-scope]`, keyframes, the reduced-motion rule), `_base` (page, text, links, focus) and `_controls` (class-based primitives: `.btn` + `--primary/--secondary/--ghost/--danger/--block`, `.field*`, `.plate`, `.eyebrow`, `.micro-label`, `.divider`, `.link-btn`). There are no bare `button`/`input`/`label` rules. New UI follows the root `DESIGN.md` only — it is the design system's source of truth, and UI it doesn't cover is undecided until added there. Legacy styles (the kept `src/styles/` mixin partials and existing component `.scss`) are frozen.
- **Themed root**: the app root carries `data-grm`, `data-theme-scope` and `--theme-*` bound from `IdentityService.roles()` (the active profile's colors, or the default R → U → G). `ThemedModal` is its own themed root. `ThemeService` is a legacy adapter over `IdentityService` for old components.
- **Partials kept**: `_breakpoints.scss` (`$bp-mobile: 640px`, `$bp-wide: 960px`, `mobile`/`wide` mixins). `_modal.scss`/`_dropdown.scss` are legacy mixin-only partials for old components — not for new UI.
- `angular.json`'s `stylePreprocessorOptions.includePaths` includes `src/styles`, so any component `.scss` can `@use 'breakpoints' as bp;` without relative `../../../` paths.
- **Typefaces**: Grenze (display, 600/700) + Karla (400–700), loaded via a Google Fonts `<link>` in `src/index.html` (`font-display: swap`); tokens `--font-display`/`--font-sans`.
- **Page shell**: `app.html` renders `<app-top-bar />`, then the legacy `.app-layout` (nav drawer + `<main class="app-shell">` with the `<router-outlet>`), then `<app-entry-modal />`. The root host is a two-row grid (`auto minmax(0, 1fr)`) filling `100dvh`; `.app-shell` is the default scroll region. The scroll area (`main.view-area`) pads its end by `--bottom-bar-height`, which a screen-fixed bottom bar (the Planechase phone dock) sets on the root element while mounted, so the last content (the legal notice) scrolls clear of it. View-level `.scss` files should not set their own max-width/centering.
- **Nav bar** (`src/app/shared/layout/nav-bar/`, legacy) is a mobile-first grouped side drawer; its host uses `:host { display: contents; }` so the drawer pins open as a sidebar at `bp.wide`. Its `--nav-bar-height` math refers to a token the new foundation no longer declares.
- **Legacy component idioms** still in use by old components: custom checkboxes via `:has()` (a real `<input type="checkbox">` at `opacity:0` with a styled sibling), and the rotated-scatter card spread shared by `card-search-panel` and `collection-card-grid`.
