## Architecture

- **Angular 22, standalone components, zoneless** (no `zone.js` dependency) — change detection relies on signals/explicit triggers, not zone patching. Bootstrapped in `src/main.ts` via `bootstrapApplication`.
- **No UI component framework.** Ionic and Angular Material were both evaluated and removed; components and styles are hand-written (plain HTML/SCSS per component).
- **`ChangeDetectionStrategy.OnPush`** is set on every component and is the schematic default for `ng generate component` (configured in `angular.json`). New components should keep it unless there's a specific reason not to.
- **Path aliases**: `@models/*`, `@services/*`, `@testing/*` map to `src/app/core/{models,services,testing}/*`; `@shared` (bare) resolves to the `src/app/shared/index.ts` barrel, `@shared/*` to individual files under `src/app/shared/`. Configured in `tsconfig.json`. Use these instead of relative `../` imports when crossing into `core` or `shared` from elsewhere; within `shared` itself, cross-component imports use `@shared/deep-path` (not the barrel) to avoid circular imports through `index.ts`.
- **`src/app/shared/` is organized into domain subfolders** — `cards/`, `decks/`, `locations/`, `auth/`, `layout/`, `effects/`, `common/` — rather than one flat list of component folders. Place new shared components in the matching domain folder (or `common/` for subject-agnostic primitives); `@shared/*` still resolves through the nesting unchanged.
- **Routing**: `src/app/app.routes.ts` is the single source of route definitions. Route-level ("page") components live under `src/app/views/<name>/`, one folder per view, each with its own `.ts`/`.html`/`.scss`/`.spec.ts`. `home` is the current example and is mounted at the root path (`''`).
- **App shell**: `src/app/app.ts` is the root component. See "Styling / design system" below for its template/layout structure.
- **Static assets** go under `public/assets/` and are served at `/assets/...` at runtime (configured via the `assets` glob in `angular.json`'s build target, which copies everything under `public/` to the app root).
- **Capacitor** (`capacitor.config.ts`) wraps the built web app (`dist/grimorio/browser`, must match the `build` target's output path) for native targets. The `android/` platform has been added (via `npx cap add android`, with `@capacitor/android` as a devDependency) — it's a generated Gradle project, not hand-edited; run `npm run cap:build` after web changes to resync it. No `ios/`/`electron/` platforms have been added.
- **Testing**: unit tests run through Angular CLI's `@angular/build:unit-test` builder, backed by Vitest (not Karma, not Jest) — this is Angular's current default runner and is wired into the same esbuild-based pipeline as `ng build`/`ng serve`.
- **OCR**: `tesseract.js` provides client-side text recognition (used by card scanning to read a card's set code/collector number from a photo). It must always be loaded via dynamic `import()`, never a static import, so it stays out of the initial bundle — the CLI's esbuild-based builder code-splits it into its own lazy chunk automatically. Worker/wasm/language-data assets are fetched from tesseract.js's default CDN at runtime (no assets committed to the repo).
- **`src/app/core/utils/`** holds framework-agnostic pure functions (e.g. `card-ocr.util.ts`). Angular's Vitest builder doesn't support `vi.mock` on relative imports — a util that needs to be mocked in a component test should be wrapped in a thin `providedIn: 'root'` service (see `CardOcrService`) so it can be swapped via a TestBed provider instead.
- **`linkedSignal`** is the idiom for writable local state that resyncs from an input/signal (e.g. `card-add-detail-panel.ts`'s `faceIndex`, reset to `0` whenever `candidate` changes) — distinct from `computed` (pure derivation, not writable) and `effect` (side effects, not state derivation).

## Domain model

- **`CardEntry`** (`src/app/core/models/card.model.ts`) — a printing-level owned card record: identity fields (scryfallId/oracleId, set/collector number, name, rarity, colorIdentity, typeLine, commanderLegality, canBeCommander), physical/ownership fields (finish, language, condition, quantity, `locationId`, forSale, notes), and an optional double-faced `faces[]`.
- **`StorageLocation`** (`src/app/core/models/storage-location.model.ts`) — `{id, name, parentId}`, plus a derived `StorageLocationNode` tree type for nested physical storage.
- **`Deck` / `DeckCard`** (`src/app/core/models/deck.model.ts`) — a `Deck` has `commander: DeckCard | null` and `cards: DeckCard[]`. `DeckCard` is a union: `{source: 'owned', cardEntryId}` referencing an existing `CardEntry`, or `{source: 'freeBuild', card: DeckCardIdentity}` embedding a standalone printing-level identity for cards not in the collection. Both variants are printing-precise (set/collector/finish-level) — never a generic "any printing" reference.
- **Persistence pattern**: `CardService`, `StorageLocationService`, `DeckService` (`src/app/core/services/`) all follow the same shape — signal-backed state hydrated asynchronously from **IndexedDB** (via the `idb` library, `src/app/core/db/`) on construction, with full CRUD and `byId` computed lookups. Each service exposes `whenReady()` (resolves once initial hydration lands) and `flush()` (resolves once all enqueued writes have landed) — `whenReady()` is awaited app-wide via a `provideAppInitializer` in `app.config.ts`, so no component ever observes pre-hydration state. Writes go through a private serialized queue (`enqueueWrite`) per service. New entity services should follow this convention. A one-time, idempotent migration (`src/app/core/db/local-storage-migration.ts`) moves any pre-existing `localStorage` data into IndexedDB on first load after this shipped; new code should never read/write the old `grimorio.*` localStorage keys directly. Unit tests need the `fake-indexeddb` polyfill (wired via `src/test-setup.ts`, loaded through `angular.json`'s `setupFiles`) since jsdom has no native IndexedDB.
- **Card data source**: `CardLookupService` (`src/app/core/services/card-lookup.service.ts`) resolves a set code + collector number against a **Supabase**-hosted catalog (`printings` joined to `cards` tables; client in `src/app/core/supabase-client.ts`). There is no live Scryfall API integration and no price data modeled anywhere. Multi-row lookups (`lookupManyByScryfallIds`, `lookupManyBySetCode`, used by CSV import) batch into one query per distinct key instead of one query per row — new bulk-lookup call sites should follow the same batching shape rather than looping a per-row Supabase call.
- **New Supabase tables**: must ship GRANT statements and owner-only RLS policies (`(select auth.uid()) = user_id`, see `storage_locations`/`card_entries`) in the same migration that creates the table, and any `updated_at` column must be `NOT NULL` with a default — a table without these is unusable from the client and null timestamps break last-write-wins sync reconciliation.
- **Sync**: `CardEntry`/`StorageLocation` both require `updatedAt: string` (ISO timestamp), stamped internally by `CardService`/`StorageLocationService`'s `add`/`update`/`addMany` — callers never pass it themselves, same as `id`. `DeckCardIdentity` (a frozen freeBuild-deck-card snapshot) deliberately excludes `updatedAt` from its `Omit<CardEntry, ...>`. Both services also track soft-delete tombstones (IndexedDB's `tombstones` store), populated by `remove()` and exposed via `getTombstones()`/`clearTombstones()` — sync-only, invisible to every other consumer. `SyncService` (`src/app/core/services/sync.service.ts`) does manually-triggered (no background) push/pull against Supabase's `storage_locations`/`card_entries` tables for the signed-in user, via a generic reconciler (`reconcileEntities`, `src/app/core/utils/sync-reconcile.util.ts`) using per-row last-write-wins on `updatedAt`; tombstones resolve the "deleted here vs. never synced" ambiguity a remote-only row would otherwise have. No UI trigger exists yet. Not extended to decks — the prototype `decks`/`deck_cards` Supabase tables were dropped and need redesigning from scratch, not resurrecting.
- **Mana/card symbol assets**: `public/assets/mana/` holds all 84 MTG mana/card symbol SVGs fetched from Scryfall's `/symbology` API plus a `manifest.json` describing each (symbol, name, colors, hybrid/phyrexian flags). Only the 5 WUBRG icons are wired up so far (the theme picker); the rest await future mana-cost rendering.

## Auth

`AuthService` (`src/app/core/services/auth.service.ts`) wraps Supabase Auth (`supabase.auth.*` on the existing `SUPABASE_CLIENT`, no extra package) with a signal-backed `session`/`user`, kept live via `onAuthStateChange`. Sign-in is entirely optional — no route guards, nothing currently restricts access based on auth state. `AuthControl` (`src/app/shared/auth-control/`) is the sign-in/sign-out widget (email + "Sign out", or a "Sign in" button) and opens `AuthModal` (`src/app/shared/auth-modal/`) for email/password sign-in or sign-up; it's embedded directly in `NavBar` (`src/app/shared/nav-bar/`) rather than a separate top-level bar, so there's a single nav strip everywhere — see "Styling / design system" below for `NavBar`'s current drawer-based layout. The Supabase project has "Confirm email" disabled, so sign-up logs the user in immediately rather than requiring an email click-through — re-enable once the app has a real deployed URL to redirect a confirmation link to.

**Modals**: use the native `<dialog>` element (`showModal()`/`close()`), not a library — `AuthModal` is the reference pattern for any future modal.

**Effect intensity reference**: `auth-modal.scss` is also the reference for animation/glow intensity — when adding or tuning an effect (spark burst, glow, hover lift) on another component, match its values to what `auth-modal` already uses rather than picking new numbers from scratch, and keep to one animated effect per element rather than stacking several (e.g. breathing glow + sheen + hover lift + text glow) on the same button.

## PWA

`@angular/service-worker` (added via `ng add @angular/pwa`) makes the app installable as a standalone desktop/mobile app. `ngsw-config.json` (project root) configures asset/data caching; `public/manifest.webmanifest` declares the app identity/icons. The service worker is registered in `src/app/app.config.ts` via `provideServiceWorker(...)`, gated on `!isDevMode()` — it's inert under `ng serve` and only active in production builds, which emit `ngsw.json`/`ngsw-worker.js` into `dist/grimorio/browser`. Icons under `public/icons/` are placeholders from the schematic, not final artwork.

## Styling / design system

- **Design tokens** live in `src/styles/` as SCSS partials (`_tokens.scss`, `_breakpoints.scss`, `_reset.scss`, `_buttons.scss`, `_forms.scss`, `_motion.scss`, `_modal.scss`), pulled into the single global stylesheet (`src/styles.scss`) via `@use`. Colors/spacing/radii/type scale are emitted as CSS custom properties on `:root` (not SCSS variables) so any component stylesheet can read them directly via `var(--space-3)` etc. Breakpoints (`$bp-mobile: 640px`, `$bp-wide: 960px`) are SCSS variables with `mobile`/`wide` mixins, since custom properties can't be used inside `@media` conditions.
- `angular.json`'s `stylePreprocessorOptions.includePaths` includes `src/styles`, so any component `.scss` can `@use 'breakpoints' as bp;` without relative `../../../` paths.
- **`_forms.scss`**: baseline styling for `input[type='text']` plus global `label`, `.error`, and `.close-button`/`.back-button` rules, following the same global-tag-selector convention as `_buttons.scss` — don't redeclare these locally in new components.
- **`_motion.scss`**: shared `--ease-standard`/`--duration-fast/base/slow` timing tokens, `@keyframes spin` + `.spinner`, the `.spark`/`@keyframes spark-burst` effect (tunable per-caller via `--spark-peak-opacity`/`--spark-end-scale`/`--base-angle`/`--spread`/`--dur` — a caller's own component stylesheet can override these because Angular's compiled selectors are more specific than the plain global `.spark` class), and the typed `--core-color` custom property (`@property`, syntax `<color>`) + `@keyframes core-color-cycle` for smoothly cycling through all of a user's chosen identity colors (see the theme-role retinting convention below). New components needing transitions/animations/burst effects should reuse these instead of hand-rolling new keyframes.
- **`_modal.scss`**: mixins for shared `<dialog>`-based modal chrome — `modal-surface`, `modal-scroll-body` (includes `themed-scrollbar($axis)`, reusable for any scroll container, not just modals), `dialog-mobile-fullbleed`, `dialog-reduced-motion`, `theme-ring`/`theme-ambient-glow` (the conic-gradient ring/halo retinting recipe), and `glow-button`. New modals should reuse these instead of re-copying `auth-modal`'s CSS.
- **Grid-rows accordion**: `display: grid; grid-template-rows: 0fr` → `1fr` on a wrapper with `overflow: hidden` on its inner child animates a block's height without JS measurement (used in `auth-modal`). Pair a collapsed wrapper with `[attr.inert]` when it holds a focusable control, so it's skipped from the tab order while hidden. A negative margin used to "reclaim" ring/glow padding doesn't survive being the first/last child of such an `overflow: hidden` auto-sized ancestor — give the ring real, uncompensated padding instead.
- Prefer CSS relative-color syntax (`rgb(from var(--x) r g b / pct%)`) over `color-mix()` for alpha-blended glow effects — shorter compiled output for the same result, same browser baseline (see `auth-modal.scss`).
- **Typefaces**: Grenze (display) + Karla (sans), loaded via Google Fonts `<link>`s in `src/index.html` (`font-display: swap`, not self-hosted); tokens `--font-display`/`--font-sans`. `body` sets `font-family: var(--font-sans)`, and controls inherit via `font: inherit`. `--font-display` is reserved for card names and page/section titles only.
- Custom checkboxes use `:has()`: a real `<input type="checkbox">` stays in the DOM at `opacity:0` for keyboard/AT behavior, with a sibling `.checkbox-box`/glyph styled via `.checkbox-field:has(:checked)` — reuse this instead of `appearance: none` hacks. A bare class selector for a checkbox row's `flex-direction: row` can lose to an earlier, more specific combinator selector despite CSS source order — qualify the override (e.g. `.right-column label.checkbox-field`) rather than relying on declaration order.
- The rotated-scatter card spread (seeded `sin()`/`cos()` transform, hover un-rotate+lift+scale, multicolor conic ring), originally in `card-search-panel.scss`, is a shared idiom for card-art grids — also used by `collection-card-grid` (`src/app/shared/collection-card-grid/`) for the Collection Detail grade view.
- **Page shell**: `src/app/app.html` wraps `<router-outlet>` in `<main class="app-shell">`; `app.scss` owns the page's max-width/centering/gutters. View-level `.scss` files should not set their own max-width/centering — only internal spacing. The app fills exactly `100dvh` and never scrolls at the `html`/`body` level: `.app-shell` is the default scroll region (`overflow-y: auto`) for every view's content. A view needing a different scroll shape (e.g. only one inner region scrolling, like `collection-detail`) opts out locally via `:host { overflow: hidden }` and owns its own scrolling descendant instead. `--nav-bar-height` (`_tokens.scss`) is the authoritative nav-bar height the shell math is built on — `nav-bar.scss` sets its own height from it rather than deriving it from padding.
- **Buttons**: no `<app-button>` component — a global baseline in `_buttons.scss` styles the raw `button` element, with `.btn-primary`/`.btn-danger` as opt-in utility classes for key CTAs.
- **Nav bar** (`src/app/shared/nav-bar/`) is a mobile-first grouped side drawer, not a top link row: its host uses `:host { display: contents; }` so its top bar/drawer/backdrop become direct grid items of `.app-layout` in `app.html`, letting the drawer pin open as a sidebar at `bp.wide` instead of overlaying. Nav links are grouped under `<section class="drawer-group">` (currently one "Collection" group) so future sections (Play tools, Learn/rules) are additive.
- **Theme-role retinting convention** (`ThemeService.roles()`, `src/app/core/services/theme.service.ts`): lets a component retint itself to the user's own chosen identity colors (1-3 MTG colors) instead of the app's default brand orange/cyan, scoped to that component only (not a global token swap). Each consumer (1) binds `roles().primary/accent/tertiary(-hover)` onto its own host as component-prefixed custom properties, either via template `[style.--x]` bindings (`auth-modal.html`) or an Angular `host: {}` metadata object (`add-card-modal.ts`, `collection-header.ts`, `collection-detail.ts` — the more scalable of the two, preferred for new components); then (2) aliases those down to short local names with a fallback chain, e.g. `--mp: var(--modal-primary, var(--color-primary));`, and uses only the short alias everywhere else in that stylesheet. Two fallback rules matter and are easy to get backwards: **tertiary falls back to accent, not primary** (`--mt: var(--modal-tertiary, var(--ma))`), so a 2-color pick still reads as a coherent primary/accent pair rather than a mismatched primary/primary one; and **accent/tertiary both bottom out at primary**, not a separate default color, so a single-color pick reads as fully monochrome. `auth-modal.scss` is the original/reference implementation (`--mp/--ma/--mt`); other consumers follow the same shape with their own prefix (`--cmp`/`--chp`/`--cdp`/etc.). A shared cross-component animation that needs to read these without hardcoding any one consumer's prefix (e.g. `core-color-cycle`, see `_motion.scss`) instead reads generic `--identity-primary/-accent/-tertiary` names, which each consumer aliases to its own short names — see `collection-header.scss`/`leyline-field.scss`/`collection-detail.scss` for that bridge. Short local aliases also help keep compiled component CSS under the `anyComponentStyle` 8kB budget in `angular.json`. The convention is confirmed general-purpose, not modal-specific — it's used on page-level components (`collection-header`, `collection-detail`) as well as modals (`auth-modal`, `add-card-modal`).
