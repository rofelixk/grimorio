## Architecture

- **Angular 22, standalone components, zoneless** (no `zone.js` dependency) — change detection relies on signals/explicit triggers, not zone patching. Bootstrapped in `src/main.ts` via `bootstrapApplication`.
- **No UI component framework.** Ionic and Angular Material were both evaluated and removed; components and styles are hand-written (plain HTML/SCSS per component).
- **`ChangeDetectionStrategy.OnPush`** is set on every component and is the schematic default for `ng generate component` (configured in `angular.json`). New components should keep it unless there's a specific reason not to.
- **Path aliases**: `@models/*`, `@services/*`, `@testing/*`, `@utils/*`, `@data/*`, `@db/*` map to `src/app/core/{models,services,testing,utils,data,db}/*`; `@shared/*` maps to `src/app/shared/*` (there is no barrel). Configured in `tsconfig.json`. A relative `../` import into `core/` or `shared/` from outside that area is a lint error; relative imports within one area are allowed.
- **`src/app/shared/` is organized into domain subfolders** — `auth/`, `cards/`, `collections/`, `decks/`, `ds/`, `effects/`, `gameplay/`, `layout/` — rather than one flat list of component folders. Place new shared components in the matching domain folder; `ds/` holds the new design-system primitives (DESIGN.md), `gameplay/` the Planechase components and flairs, `effects/` the page sweep; `@shared/*` still resolves through the nesting unchanged.
- **Routing**: `src/app/app.routes.ts` is the single source of route definitions. Route-level ("page") components live under `src/app/views/<name>/`, one folder per view, each with its own `.ts`/`.html`/`.scss`/`.spec.ts`. `home` is the current example and is mounted at the root path (`''`). The collection area is one matcher route (`collectionMatcher`): `/collection`, `/collection/{id}` and `/collection/caixa` all render one reused `CollectionArea` view, fed `ref` through `withComponentInputBinding`. The deck area works the same way (`deckMatcher`): `/decks` and `/decks/{id}` render one reused `DeckArea`, so the list and a deck page can share the DOM during the page change. An area with pages creates its page change with `injectPageChange({ ...RULE, target })` (`shared/effects/page-sweep/page-change.ts`), passing a pure `PageRule` from `core/utils/*-pages.util.ts`, and renders it through `<app-page-sweep [change]>` with one projected `<ng-template [appPagePlace]>`. A navigation that must swap instantly passes `info: NO_SWEEP_INFO`.
- **App shell**: `src/app/app.ts` is the root component. See "Styling / design system" below for its template/layout structure.
- **Static assets** go under `public/assets/` and are served at `/assets/...` at runtime (configured via the `assets` glob in `angular.json`'s build target, which copies everything under `public/` to the app root).
- **Capacitor** (`capacitor.config.ts`) wraps the built web app (`dist/grimorio/browser`, must match the `build` target's output path) for native targets. The `android/` platform has been added (via `npx cap add android`, with `@capacitor/android` as a devDependency) — it's a generated Gradle project, not hand-edited; run `npm run cap:build` after web changes to resync it. No `ios/`/`electron/` platforms have been added.
- **Testing**: unit tests run through Angular CLI's `@angular/build:unit-test` builder, backed by Vitest (not Karma, not Jest) — this is Angular's current default runner and is wired into the same esbuild-based pipeline as `ng build`/`ng serve`. jsdom has no `showModal()`/`close()`: specs that mount a `<dialog>` call `stubDialog()` from `@testing/dialog` and restore it after destroying the component. jsdom has no `ResizeObserver` either: height code is driven with `installResizeObserver()`/`notifyResize()`/`restoreResizeObserver()` from `@testing/resize-observer`, with `offsetHeight` set through `Object.defineProperty`; `IntersectionObserver` likewise through `installIntersectionObserver()`/`intersect()`/`restoreIntersectionObserver()` from `@testing/intersection-observer`. Unit specs carry no bulk-data or performance cases (thousands of cards or entries, timing thresholds): they made a Vitest worker run out of memory, and volume and bandwidth checks are run manually.
- **Lint and budgets**: `npm run lint` is the ESLint CLI over `src/` (`eslint.config.js`, type-aware via `projectService`). `@typescript-eslint/no-floating-promises` and `no-misused-promises` are errors; `void` marks a deliberate fire-and-forget promise. `@angular-eslint/prefer-signals` and `prefer-output-emitter-ref` only warn. The production build enforces the budgets in `angular.json`: `initial`, `anyComponentStyle`, and one named `bundle` budget per lazy chunk (`cards-json`, `cards-pt-br-json`); a new lazy chunk gets its own named budget.
- **Planechase card data**: `src/app/core/data/planechase/` ships `cards.json` (planes/phenomena with image URLs and a text hash) and `cards.pt-br.json` (reviewed translations keyed by id, each with the `sourceHash` it was made from). Both are generated by the maintainer (`npm run sync:planechase`, then the `planechase-translate` skill) and never edited by hand. `PlanechaseCatalogService` loads them only via dynamic `import()` (own lazy chunk), through `planechaseCatalogResolver` on the `/modes/planechase*` routes; a stale or missing translation falls back to English. A static `import` of `cards.json`/`cards.pt-br.json` is a lint error, specs included. The app makes no Supabase call for Planechase. `default-off.ts` in the same folder is a hand-kept (not generated) list of oracle ids that start disabled: `enabledCards(cards, null)` excludes them while no selection is saved, and the deck settings' draft starts from them (`initialDisabledIds`). A saved selection alone decides; the list is never written or synced.
- **`src/app/core/utils/`** holds framework-agnostic pure functions (e.g. `identity.util.ts`). Angular's Vitest builder doesn't support `vi.mock` on relative imports — a util that needs to be mocked in a component test should be wrapped in a thin `providedIn: 'root'` service so it can be swapped via a TestBed provider instead.
- **`linkedSignal`** is the idiom for writable local state that resyncs from an input/signal (e.g. `ShellState.drawerOpen` in `core/services/shell-state.service.ts`, reset to closed whenever `wide` changes) — distinct from `computed` (pure derivation, not writable) and `effect` (side effects, not state derivation).
- **Timers, effects and router events**: a timer is kept only when its duration is the behavior (a visible duration, hover or press delay, network or storage timeout, periodic clock, cooldown or emission), or as the recorded fallback for an event that may never fire, paired with that event. Anything that waits for an animation or another part of the app waits for its end event or its state. `effect`/`afterRenderEffect` only change something outside the reactive state (DOM, focus, storage, the browser, a timer or listener they own), and a value derived from other state is `computed` or `linkedSignal`. A router-event subscription is kept only when each event in order matters; a consumer of the latest navigation reads `Router.currentNavigation()`/`lastSuccessfulNavigation()`. Every one is released on destroy.

## Domain model

- **`CardEntry`** (`src/app/core/models/card.model.ts`) — a printing-level owned card record: identity fields (scryfallId/oracleId, set/collector number, name, rarity, colorIdentity, typeLine, commanderLegality, canBeCommander), physical/ownership fields (finish, language, condition, quantity, `locationId`, forSale, notes), an optional double-faced `faces[]` and `artist`, and `addedAt` (stamped by `add`, never changed; card lists are newest-added first).
- **`Collection`** (`src/app/core/models/collection.model.ts`) — `{id, name, color, parentId, updatedAt}`, nested up to 3 levels; `color` is one of the 16 palette ids in `COLLECTION_COLORS`. Counts, depth and kind (empty / cards / subcollections) are never stored: `CollectionService` derives them from `CardService.cards()` (`computeStats`, `core/utils/collection-tree.util.ts`). The holding box ("Caixa temporária") is derived too — every card whose `locationId` matches no collection — so moving cards there writes no card at all.
- **`Deck`** (`src/app/core/models/deck.model.ts`) — `{id, name, format, updatedAt}`, `format` one of the 8 `DECK_FORMATS` ids (names and rules live in `DECK.formats`, `core/utils/deck-copy.ts`). A deck is a card location: a card in a deck carries the deck id in `CardEntry.locationId`, and the record stores no card data or counts. The holding box is every card whose `locationId` matches no collection and no deck (`computeStats` skips `DeckService.ids()`), so deleting a deck writes no card.
- **Persistence pattern**: `CardService`, `CollectionService`, `DeckService` (`src/app/core/services/`) all follow the same shape — signal-backed state hydrated asynchronously from **IndexedDB** (via the `idb` library, `src/app/core/db/`), with full CRUD and `byId` computed lookups. Owned data is partitioned per local profile: IndexedDB `grimorio-device` holds the profile registry and `activeProfileId`, and each profile has its own `grimorio-profile-{id}` database, so isolation holds by construction; the pre-profiles `grimorio` database is deleted on startup (`core/db/legacy-cleanup.ts`). Each service exposes `load(profileId | null)`, `changeCount`,  exposes `whenReady()` (resolves once the latest hydration lands) and `flush()` (resolves once all enqueued writes have landed). Entity services don't hydrate on construction; `ProfileSessionService.whenReady()` (awaited in `app.config.ts`'s initializer after `runLegacyCleanup()` and `ProfileStore.whenReady()`) calls `load(activeProfileId)` on each, so no component ever observes pre-hydration state. Writes go through a per-service `WriteQueue` (`core/db/write-queue.ts`) built by `SaveQueueService.create(label)`: a failed `enqueue` logs and shows the "Dados" toast and later writes still run; `run()` is for saves whose caller reports its own error (`remove()` on collections/decks, every `ProfileStore` write). Each write captures the bound profile DB and `boundProfileId()` when enqueued and, once landed, announces its kind through `CrossTabService` (`BroadcastChannel('grimorio-data')`, kind + profile id, no data); other open copies with that profile bound call the service's `refresh()`, which re-reads IndexedDB without clearing the signal, bumping `changeCount` or writing. New entity services should follow this convention. Both IndexedDB openers close on `versionchange` (idb `blocking`): a newer version mounts the locked `ReloadPrompt` (`StorageHealthService.reloadRequired`); a profile deleted in another copy is never reopened (`ProfileGoneError`) and this copy signs out. Specs simulate a second copy with `@testing/cross-tab`'s fake channel pair; `test-setup.ts` hides the real `BroadcastChannel`. `CardService`, `CollectionService` and `DeckService` persist per row instead of with `replaceStore` (only `CardService.applySyncResult` still rewrites its store): `writeRows(ops)` (`core/db/entity-store.ts`) applies puts/deletes across `collections`, `decks`, `cards` and `tombstones` in one transaction, so create-with-move and delete are all-or-nothing; the card side updates in memory through `CardService.applyMoved`/`applyRemoved`, which never persist on their own. Unit tests need the `fake-indexeddb` polyfill (wired via `src/test-setup.ts`, loaded through `angular.json`'s `setupFiles`) since jsdom has no native IndexedDB; `src/test-setup.ts` also resets every `grimorio-*` database before each test.
- **Planechase state**: `PlanarSelectionService` (the planar deck's disabled card ids) is an entity service in `ProfileSessionService`'s list, stored as the `planarSelection` `meta` record of the active profile's database, or of `grimorio-device` when no profile is active. `PlanechaseGameService` is device-scoped, not per profile: the game in progress (with its one-step undo) is the `planechaseGame` record in `grimorio-device`'s `meta` store, hydrated in the app initializer, and survives profile switches. `PlanarImageService` caches card images in Cache Storage (`grm-planechase-images`) and serves them as object URLs, so seen images work offline. Randomness comes from `crypto.getRandomValues` (`core/utils/crypto-random.util.ts`).
- **Card catalog**: a **Supabase**-hosted catalog (`printings` joined to `cards`), filled by `npm run sync:scryfall` from Scryfall bulk data; `printings` also carries `border_color`, `released_at`, `image_small` and `image_large`, read by `sync:planechase`, plus `artist` and `faces`. The app reads it through `CardCatalogService` (`search`, `detail`) with its own anonymous, session-less client (`grm-catalog`); the search matches `cards.search_name`, an accent-free key `sync:scryfall` writes with `searchKey` (`core/utils/card-search.util.ts`). The configuration of the removed OCR and CSV import is recorded in `backlog/reference/card-features.md`. There is no live Scryfall API integration and no price data modeled anywhere.
- **New Supabase tables**: must ship GRANT statements and owner-only RLS policies (`(select auth.uid()) = user_id`, see `collections`/`card_entries`) in the same migration that creates the table — since 2026-10-30 Supabase no longer auto-grants Data API access to new `public` tables, so a missing grant returns "permission denied". Owner-only tables: `grant select, insert, update, delete on public.<t> to authenticated;` (no `anon` grant). Public catalog tables (`cards`/`printings`): `grant select on public.<t> to anon, authenticated;`. Grant `service_role` only when server-side code needs the table. Any `updated_at` column must be `NOT NULL` with a default — a table without these is unusable from the client and null timestamps break last-write-wins sync reconciliation.
- **Sync**: `CardEntry`/`Collection`/`Deck` all require `updatedAt: string` (ISO timestamp), stamped internally by their services' `add`/`create`/`update`/`addMany` — callers never pass it themselves, same as `id`. The services also track soft-delete tombstones (IndexedDB's `tombstones` store), populated by `remove()` and exposed via `getTombstones()`/`clearTombstones()` — sync-only, invisible to every other consumer. `SyncService` (`src/app/core/services/sync.service.ts`) is an orchestrator over the step classes in `core/services/sync/` (identity, collections, decks, cards, planar selection; row mappers in `sync-rows.ts`, `fetchAll`/`upsertRows`/`deleteRows` in `sync-remote.ts`). Cloud reads of collections, decks and cards are paged (`order('id').range()`, `count: 'exact'`), and only one copy of the app syncs at a time (`SYNC_LOCK`, Web Locks API). It syncs the active profile's collections, decks, then cards with its linked account (composite `(user_id, id)` keys, `onConflict: 'user_id,id'`), then its planar deck selection as one reconciled entity (`planechase_selections`, one row per account, `onConflict: 'user_id'`, no tombstones), via a generic reconciler (`reconcileEntities`, `src/app/core/utils/sync-reconcile.util.ts`) using per-row last-write-wins on `updatedAt`; tombstones resolve the "deleted here vs. never synced" ambiguity a remote-only row would otherwise have. Collections are then repaired before upload by `repairCollectionTree` (`core/utils/collection-tree.util.ts`): orphaned subcollections are dropped (and deleted remotely), and duplicate sibling names are renamed "Nome (2)", the remote row keeping its name. Decks are then de-duplicated by `repairDeckNames` (`core/utils/deck.util.ts`): same name ignoring case and accents → "Nome (2)", the remote row keeping its name. After the card sync, `CollectionService.resolveMixedCollections(syncedAt)` moves the direct cards of any collection that also has subcollections into its first child, stamped after `syncedAt` so the next sync uploads them. Sync starts only from the shell's sync controls (`SyncStatusService.act()`) and the "Excluir perfil" step's in-place sync — never on sign-in, link or switch. Each sync first runs an identity step that reconciles the profile's colors/name with the account's `user_metadata` (`grm_colors`/`grm_label` plus `grm_colors_at`/`grm_label_at`), last-write-wins (`core/utils/identity-sync.util.ts`). The expired state comes from the profile's `cloud.needsReauth` flag, not from the last sync: `SyncService.state()` reports `'reauth'` whenever the flag is set and drops it as soon as any re-sign-in (reauth, reset code, recover) clears the flag.
- **Mana/card symbol assets**: `public/assets/mana/` holds all 84 MTG mana/card symbol SVGs fetched from Scryfall's `/symbology` API plus a `manifest.json` describing each (symbol, name, colors, hybrid/phyrexian flags). None are wired up in the app anymore; they await future mana-cost rendering. New UI must not use them (DESIGN.md: no Magic symbols).

## Auth

Local profiles (`ProfileStore`, PBKDF2 hashes) are required for owned data; cloud accounts are optional, per profile (`CloudAuthService`, e-mail + password, 6-digit reset code). Entering (pick/unlock/create a profile, reset its password) runs in `EntryModal` (`shared/auth/entry-modal/`, contexts `device | gate`) via `EntryModalService`, state in `EntryFlowStore`. Managing the active profile (colors, name, passwords, link/reauth/unlink, deleting the profile or the cloud account) runs in `ProfileModal` (`shared/auth/profile-modal/`) via `ProfileModalService`, state in `ProfileFlowStore`. Pure rules live in `core/utils/{entry-flow,profile-flow}.util.ts`; all PT-BR copy is centralized in `core/utils/entry-copy.ts`. Only one modal is ever open: each service's `open()` is a no-op while the other is open. The top-bar profile control and the shell's sync area open the profile modal. `/profile` redirects to Home.

- **Shared cloud forms**: `CloudForm`/`ResetForm` (under `entry-modal/`) render in both modals through `CloudSteps` (`shared/auth/cloud-steps.ts`: reset code, cooldown, resend, "Esqueci minha senha", "Recupere o acesso"), built on `FlowForm` (`shared/auth/flow-form.ts`: fields, errors, loading, the stale-result token, submit). Each flow store creates its own instances and keeps its public members as aliases; each modal provides its store's with `{ provide: CloudSteps, useFactory: () => inject(Store).cloud }`, never at root. `fluid-face.ts` (`shared/ds/themed-modal/`) is the themed preset over `FluidHeight` (`shared/ds/fluid-height.ts`: desktop fluid height written straight to the DOM, animated only after the first pointer or key press) and focuses the first field or action row on each screen change.
- **Deletion**: a local profile is deleted via `ProfileLifecycleService` + `deleteProfileDb(id)` (drops `grimorio-profile-{id}`), never touching the cloud. A cloud account is deleted only through the `delete_own_account()` Postgres function (`CloudAuthService.deleteAccount`).
- **Toasts**: `ToastService` (one at a time, replaced by the next, 5 s). `ToastOutlet` hosts sit in `app.html`, `ThemedModal` and the nav drawer; only the most recently pushed active host renders, as a popover, so the toast shows inside the top `<dialog>` (a modal dialog makes everything outside it inert).

- **Route gating**: `profileGuard` (`core/guards/profile.guard.ts`) gates every owned-data route; with no active profile it opens the entry modal and waits. Gated routes also set `runGuardsAndResolvers: 'always'` so a sign-out/switch re-guards the current page. Home, About and the `/modes*` gameplay routes (Planechase) stay ungated.
- **Cloud clients**: one Supabase auth client per linked profile (`CloudSessionService`, localStorage key `grm-cloud:{id}`). Cloud errors reach the UI only via `mapCloudError` (`core/utils/cloud-error.util.ts`) — never raw Supabase text.

The Supabase project has "Confirm email" disabled, so sign-up signs the account in immediately.

**Modals**: use the native `<dialog>` element (`showModal()`/`close()`), not a library — `ThemedModal` (`shared/ds/themed-modal/`) is the reference pattern for any future modal. Modal components are mounted only while open (`@if` on their service's `isOpen()` in `app.html`), so nothing idles in the DOM; `ThemedModal` opens on mount and closes (restoring focus to the opener) on destroy. `CompactModal` (`shared/ds/compact-modal/`) is the narrow single-column variant (480px ring, full-bleed with a wordmark header on phone) used by the collection dialogs: same mount/destroy contract, it focuses the content's `[data-autofocus]` element on open, and its `locked` input ignores Esc, the backdrop and ✕ while an operation runs; `closable = false` hides the ✕; `size` picks the ring (`compact` 480px, `wide` 720px with a fixed 640px face, `split` 880px for two panes); it hosts its own toast outlet; it gets its fluid height from `FluidHeight` too. Focus goes through `shared/ds/focus.ts` (`focusFirst` with `FIRST_STOP_ORDER` or `MARKED_STOP`, `captureFocus` for the opener, `focusOnChange`, `focusElement`). A dropdown whose options need thumbnails or two lines is `SelectList` (`shared/ds/select-list/`, templates `appSelectTrigger`/`appSelectOption`/`appSelectEmpty`), not a native `<select>`. Radio groups put the `RovingRadios` directive (`shared/ds/roving-radios.ts`, over `rovingIndex` in `core/utils/roving.util.ts`) on their `role="radiogroup"`; roving `tabindex` and `aria-checked` stay in the template.

## PWA

`@angular/service-worker` (added via `ng add @angular/pwa`) makes the app installable as a standalone desktop/mobile app. `ngsw-config.json` (project root) configures asset/data caching; `public/manifest.webmanifest` declares the app identity/icons. The service worker is registered in `src/app/app.config.ts` via `provideServiceWorker(...)`, gated on `!isDevMode()` — it's inert under `ng serve` and only active in production builds, which emit `ngsw.json`/`ngsw-worker.js` into `dist/grimorio/browser`. Icons under `public/icons/` are placeholders from the schematic, not final artwork.

## Styling / design system

- **New foundation**: `src/styles.scss` uses only `_tokens` (tokens implementing `DESIGN.md`, the `--role-*` chain redeclared on `[data-theme-scope]`, keyframes, the reduced-motion rule), `_base` (page, text, links, focus) and `_controls` (class-based primitives: `.btn` + `--primary/--secondary/--ghost/--danger/--block`, `.field*`, `.plate`, `.eyebrow`, `.micro-label`, `.divider`, `.link-btn`). There are no bare `button`/`input`/`label` rules. New UI follows the root `DESIGN.md` only — it is the design system's source of truth, and UI it doesn't cover is undecided until added there. Legacy styles (the kept `src/styles/` mixin partials and existing component `.scss`) are frozen.
- **Themed root**: the app root carries `data-grm`, `data-theme-scope` and `--theme-*` bound from `IdentityService.roles()` (the active profile's colors, or the default R → U → G). `ThemedModal` is its own themed root. `IdentityService.colors()` is the single source for the active profile's effective colors; `roles()` and the page-change dust read it.
- **Partials kept**: `_breakpoints.scss` (`$bp-mobile: 640px`, `$bp-wide: 960px`, `mobile`/`above-mobile`/`wide` mixins).
- `angular.json`'s `stylePreprocessorOptions.includePaths` includes `src/styles`, so any component `.scss` can `@use 'breakpoints' as bp;` without relative `../../../` paths.
- **Typefaces**: Grenze (display, 600/700) + Karla (400–700), loaded via a Google Fonts `<link>` in `src/index.html` (`font-display: swap`); tokens `--font-display`/`--font-sans`.
- **Page shell**: `app.html` renders `<app-top-bar />`, then `.shell-row` with `<app-side-nav />` (wide only, `ShellState.wide()`, `(min-width: 960px)`) and `<main class="view-area">` (the `<router-outlet>` plus `<app-legal-notice />`), then `<app-nav-drawer />` (narrow only), the two modals (each mounted only while open) and `<app-toast-outlet />`. The root host is a two-row grid (`auto minmax(0, 1fr)`) filling `100dvh`; `main.view-area` is the only scroll container. It pads its end by `--bottom-bar-height`, which a screen-fixed bottom bar (the Planechase phone dock) sets on the root element while mounted, so the last content (the legal notice) scrolls clear of it. View-level `.scss` files should not set their own max-width/centering.
- **Navigation** (`src/app/shared/layout/`): `top-bar` holds the wordmark plus `sync-status` and `profile-control` (wide), or a Menu button (narrow). On wide screens `side-nav` is a collapsed thread that expands on hover or focus, or stays pinned (per device, `grm-nav-pinned`); on narrow screens `nav-drawer` is a native modal `<dialog>` on the right edge with the account block. Both render `nav-links` over `NAV_DESTINATIONS` (`nav-links/nav-destinations.ts`). `ShellState` owns the wide, pinned and drawer state.
