# Research: Planar Card Preview in Deck Settings

The spec left no NEEDS CLARIFICATION markers. Each entry below settles an implementation question
the spec and the handoff (`design_handoff_planar_card_preview/README.md`) leave open, or a
conflict with the existing code.

## R1. The preview image is the tile's image (spec amended: FR-004, SC-006)

- **Decision**: The preview shows `card.images.large` through the existing `PlanarImage` /
  `PlanarImageService`, the same address the tile already shows. FR-004 and SC-006 are reworded
  so they no longer promise that "no large image loads until a preview opens". Now they say the
  preview adds no downloads of its own beyond the previewed card's large image, and never
  prefetches other cards.
- **Rationale**: Spec 006 (DESIGN.md "Card tile": *"Tiles use the card's large image, so its text
  is readable"*) already loads `images.large` for every tile near the viewport, so the old SC-006
  couldn't hold without making the tiles worse. Because `PlanarImageService.url()` memoizes an
  object URL per address, a preview of a tile that's already loaded shows its image at once, from
  memory and without a new request. The spec lets behavior conflicts be settled by updating it.
- **Alternatives considered**: *Tiles switch to `images.small`* (~10 KB, 146 × 204 px). That's
  blurry in the 1-column phone grid (~340 px wide), and it reverses a DESIGN.md decision.
  *Tiles use `small` on desktop and `large` on phones*: two images per card and cache entries for
  both, for little gain.

## R2. Where the default-off list lives and how it applies (FR-016–FR-018)

- **Decision**: A hand-kept `src/app/core/data/planechase/default-off.ts` exports
  `DEFAULT_OFF_IDS: readonly string[]`, the 8 oracle ids (verified against `cards.json`, see
  data-model.md), each with its card name in a comment. `enabledCards(cards, null)` in
  `planar-selection.util.ts` returns the catalog minus those ids, instead of every card. The deck
  view's `draft` `linkedSignal` seeds from `selection?.disabledIds ?? DEFAULT_OFF_IDS`. Nothing is
  written: `PlanarSelectionService` keeps `null` as "never saved", and sync keeps skipping the
  upload when the local selection is `null`.
- **Rationale**: `enabledCards` is already the single place both the game view (start and
  validation) and the deck view's restart check read "which cards are in", so this covers
  FR-017's "everywhere the saved selection applies" in one line. It's a `.ts` constant rather
  than JSON because it's hand-kept, not generated (FR-016), and a typed import needs no lazy
  chunk (8 short strings).
- **Alternatives considered**: *Writing the default as a saved selection on first load*. That
  breaks FR-018 (a later list change would have to migrate it), and it would make sync upload a
  selection nobody chose. *A `defaultOff` flag in `cards.json`*: the file is generated, and
  FR-016 says the list isn't generated by the script.

## R3. Input model: Pointer Events, split by `pointerType`

- **Decision**: The tile listens to `pointerenter`/`pointerleave` (hover, only when `pointerType`
  is `mouse` or `pen`), `pointerdown`/`pointermove`/`pointerup`/`pointercancel` (long-press, only
  when it's `touch`), `contextmenu` (always `preventDefault()`; opens the dialog unless a touch
  hold is in progress or just fired), `keydown` (`ContextMenu`, or `F10` with Shift) and `click`
  (toggle, swallowed once after a fired hold). The popover has its own
  `pointerenter`/`pointerleave` to hold itself open.
- **Rationale**: One event family covers mouse, pen and touch on hybrid devices (spec edge case),
  and `pointerType` separates them per gesture, not per device. Android fires `contextmenu` on a
  long-press, so treating a touch `contextmenu` as "no-op" keeps the timer (not the browser)
  deciding when the hold completes.
- **Alternatives considered**: *`mouseenter` plus `touchstart`*: two families that double-fire on
  hybrid devices. *Media queries to pick a mode*: they describe the device, not the gesture in
  progress.

## R4. Popover placement: `position: fixed`, a pure placement function

- **Decision**: The popover is rendered by the deck view (one instance, outside the tile grid),
  `position: fixed`, with coordinates from a pure `placePopover()` in
  `@utils/planar-preview.util.ts`. The inputs are the tile's rect, the popover's size, the
  viewport width and the vertical bounds (the view area's top and the deck footer's top). It
  puts the popover to the right of tiles in the left half of the grid and to the left otherwise,
  12 px from the tile, with `top` clamped between the bounds. If neither side fits, it centers
  horizontally and goes above or below the tile, whichever has more room. It recomputes on the
  view area's `scroll`, on window `resize`, and on a `ResizeObserver` of the popover (image load,
  text length).
- **Rationale**: Viewport rects make the "fully inside the window, never covering the tile" rule
  (FR-006, SC-004) directly checkable in a unit test, with no offset-parent math. Nothing
  between the view and the root sets `transform`/`filter`/`contain`, so `fixed` resolves to the
  viewport. The handoff lets the overlay mechanism be whatever is simplest. Its "columns 1–2 →
  right" rule becomes "tile center in the left half of the grid", which works for any number of
  columns.
- **Alternatives considered**: *`position: absolute` inside the grid wrapper* (the handoff's
  sketch): it needs offsets relative to the scroll container and footer, recomputed on the same
  events anyway. *CSS anchor positioning*: not in Firefox or older Android WebViews yet.
  *The Popover API with `popover="manual"`*: the top layer would lift it over the sticky footer,
  and the spec wants it kept below.

## R5. The preview dialog is its own component, not `ThemedModal`

- **Decision**: A new `PlanarPreviewDialog` (`shared/gameplay/planar-preview-dialog/`) follows
  ThemedModal's lifecycle pattern: a native `<dialog>`, `showModal()` on mount (after the first
  render), `close()` on destroy, `cancel` handled with `preventDefault()` plus a `closed` output,
  and a backdrop click detected as `event.target === dialog`. It doesn't restore focus to the
  opener. The owner focuses the tile of the card on screen after closing (FR-009a, FR-011). The
  wide variant reuses the ring look. `themed-modal.scss`'s `.ring` rules move into a `_ring.scss`
  partial next to `_face.scss`, which both components `@use`. The variant (`narrow` for 640 px or
  less, `wide` otherwise) is read once from `matchMedia` in the owner when the dialog opens, and
  passed in as an input.
- **Rationale**: ThemedModal brings things the preview doesn't want: the halo and sparks
  slot (the handoff says no halo, no sparks), its own theme root, a toast outlet, and
  restoring focus to the opener, which is wrong once Anterior/Próxima moved. Its mount-equals-open
  pattern is the one architecture.md asks new modals to follow. Extracting the ring partial keeps
  one definition of the rotating ring.
- **Alternatives considered**: *Adding `halo`/`restoreFocus` inputs to ThemedModal*: this piles
  preview-only switches onto the shell both auth modals depend on. *Copying the ring CSS*: two
  definitions drift.

## R6. System back closes the dialog, never the deck settings

- **Decision**: When the dialog opens, the controller calls
  `history.pushState({ ...history.state, planarPreview: true }, '')` (same URL). A `popstate`
  listener, attached only while the dialog is open, closes it. Closing any other way (✕, Esc,
  backdrop, route leave) calls `history.back()` when the pushed entry is still the current one.
  This happens on every device, not only on mobile: the Android WebView (Capacitor) and desktop
  browsers' back button both map to history.
- **Rationale**: Spreading the existing state keeps Angular Router's `navigationId`/page-id
  bookkeeping intact. A `popstate` back to the same URL is a same-URL navigation, which the router
  ignores by default (`onSameUrlNavigation: 'ignore'`; `app.config.ts` doesn't override it), so
  the deck view and its draft stay. Capacitor's Android default back handler calls
  `history.back()` when the WebView can go back; there's no `@capacitor/app` handler in the repo
  to intercept it.
- **Alternatives considered**: *`Location.go()`*: it runs the router's URL-change notifications
  for nothing. *A `canDeactivate` guard*: it blocks route leaving, but the back press would still
  pop the history entry, and the spec wants the dialog closed, not a "leave?" prompt.

## R7. Long-press without the browser's side effects

- **Decision**: The tile button gets `-webkit-touch-callout: none; user-select: none;
  touch-action: pan-y`, and its `<img>` gets `draggable="false"` and `pointer-events: none`
  (through a `PlanarImage` host class, since the image is inside that component). The hold uses
  a 500 ms timer started on touch `pointerdown`. It's cancelled by `pointermove` beyond 8 px
  (Euclidean), `pointerup`, `pointercancel` (the browser taking the gesture for a scroll) or
  `pointerleave`. When it fires, a `holdFired` flag makes the next `click` a no-op and resets
  itself. While the hold builds, the tile gets an `is-holding` class for the growing glow.
- **Rationale**: This is the handoff's recipe. `touch-action: pan-y` keeps vertical scrolling
  native and makes the browser fire `pointercancel` when it takes over, which is exactly the
  "scroll cancels the hold" case (User Story 2, scenario 5).
- **Alternatives considered**: *`touch-action: none`*: kills scrolling on the 1-column phone
  grid, where tiles fill the screen.

## R8. Input-dependent hint text

- **Decision**: A `hoverCapable` signal in the deck view, fed by
  `matchMedia('(hover: hover) and (pointer: fine)')` with a `change` listener, picks
  `DECK.hintPointer` or `DECK.hintTouch`. The existing `DECK.hint` is replaced (early
  development, no compatibility copy kept).
- **Rationale**: `(hover: hover) and (pointer: fine)` is true on touchscreen laptops, whose primary
  input is the trackpad or mouse. That gives FR-008a's "hybrid gets the pointer version".
- **Alternatives considered**: *`any-hover`*: true on a phone with a paired mouse, which would
  hide the long-press hint from a phone user.

## R9. State ownership: a view-scoped `PlanarPreviewController`

- **Decision**: `views/planechase-deck/planar-preview.controller.ts` is an `@Injectable()`
  provided in `PlanechaseDeck`'s `providers`. It owns the `preview` signal
  (`{ id, mode: 'popover' | 'dialog' } | null`), the open/close timers, the popover anchor, the
  history entry, and `visibleOrder` / `position` computeds built from the view's `sets` and
  `collapsed`. The view wires the tiles' outputs to it and reads its signals. An `effect` closes
  the preview when `confirming()` turns true or its card's set collapses (FR-013), and
  `DestroyRef` closes it and clears the timers on route leave.
- **Rationale**: `PlanechaseDeck` is 140 lines of draft logic. Timers, history and placement would
  more than double it. A view-scoped service is created and destroyed with the view, so no state
  outlives the page (spec: no saved state).
- **Alternatives considered**: *Everything in `PlanechaseDeck`*: harder to test in isolation.
  *A root service*: state would survive route changes for no reason.

## R10. Testing pointer gestures under Vitest/jsdom

- **Decision**: Unit tests drive the tile and controller with `vi.useFakeTimers()` and synthetic
  events. If jsdom's `PointerEvent` is missing, a `MouseEvent` carrying a `pointerType` property
  (a small helper in `@testing/`) stands in. `placePopover`, `visibleOrder` and `enabledCards`
  are pure and tested directly. Visual and real-device checks (the glow, native long-press
  suppression, the Android back button) go through quickstart.md with the `run` skill and a real
  phone.
- **Rationale**: jsdom has no layout (every rect is 0) and no native gesture handling, so the
  geometry is kept in pure functions and the gesture logic tested at the event level.
